# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

PERKIWeb is the platform for PERKI Aachen (a church fellowship): prayer requests, schedules, service takeaways, and member management. Next.js 16 **App Router** (`src/app/`), React 19, tRPC 11, NextAuth v5 (beta), Drizzle ORM, Tailwind CSS 4, shadcn/ui. Deployed on Vercel.

## Commands

Package manager is **pnpm**.

- `pnpm dev` — start dev server
- `pnpm build` — production build (Turbopack; set `SKIP_ENV_VALIDATION=1` to build without real env vars)
- `pnpm lint` / `pnpm format` — Biome check / check --write (ultracite presets, config in `biome.jsonc`; DB migrations are excluded)
- `pnpm typecheck` — `tsc --noEmit` (TypeScript 7)
- `pnpm check` — lint + typecheck + unit/integration tests; run before calling work done
- Database (Drizzle Kit, PostgreSQL): `pnpm db:dev` / `pnpm db:dev:down` (local dev Postgres, `compose.dev.yml`, port 54320, persistent volume), `pnpm db:generate`, `pnpm db:migrate`, `pnpm db:push`, `pnpm db:studio`, `pnpm db:seed`
- Local development uses the Docker dev database (`.env.example` points there): `pnpm db:dev && pnpm db:migrate && pnpm db:seed`. Never point `.env` at production.
- **Production schema changes only through migrations, applied by CI.** `deploy:migrate` runs `pnpm db:migrate` against prod after every check passes on `main`. Never `db:push` to prod: an unrecorded change breaks later migrations (`drizzle.config.ts` and `seed.ts` refuse non-local hosts). Vercel deploys the same commit in parallel, so a migration must work with the previous release too: add columns/tables first, drop or rename in a later PR.
- drizzle applies only migrations newer than the last one recorded, so a migration generated on a branch before another migration landed on `main` is silently skipped. After rebasing onto a new migration, delete yours and re-run `pnpm db:generate`. `src/lib/db/migrations.test.ts` fails on out-of-order timestamps; `check:migrations` fails if `schema.ts` changed without a migration.

## Testing

Tests never touch a real database: integration tests use PGlite and e2e uses its own throwaway container.

- `pnpm test` (Vitest, `vitest.config.ts`) runs three projects; `pnpm test:unit` runs `unit` + `dom`, `pnpm test:integration` runs `server`:
  - `unit`: node, `src/**/*.test.ts` outside `src/server`.
  - `server`: tRPC routers against **PGlite** (in-process Postgres built from `src/lib/db/migrations`, truncated after each test). `src/test/setup-server.ts` mocks `~/server` and `~/server/auth`; call procedures with `callerFor(userId)` / `anonymousCaller()` from `src/test/caller.ts`.
  - `dom`: jsdom + Testing Library for `*.test.tsx`.
- `pnpm test:e2e:db` then `pnpm test:e2e` (Playwright, `e2e/`): builds and starts the app on :3100 against a throwaway Docker Postgres (`compose.test.yml`, port 54329, tmpfs; in a parallel checkout set `E2E_DB_PORT` and `E2E_PORT` to free ports first, since every worktree would otherwise bind the same ports and reset each other's database). `e2e/global-setup.ts` recreates the schema from the migrations and seeds the `MEMBER` account; `auth.setup.ts` saves its signed-in state. `playwright.config.ts` refuses any non-local `DATABASE_URL`. Set `E2E_SKIP_BUILD=1` to reuse an existing build. Specs share one DB and run in parallel, so create data with `uniqueSuffix()`.
- PR screenshots: write `e2e/screenshots/current.shots.ts` (gitignored; `@seed` tests run once, the rest once per screen size), run `pnpm screenshots` (phone 390px + desktop, into `screenshots/`), then `pnpm screenshots:publish` to store them on the orphan `pr-screenshots` branch and print the PR markdown. The it-stack `ship-it` skill runs this whole check → screenshot → PR flow (facts in `## it-stack` below).
- Known gaps are pinned with `it.fails` / `test.fail()` and a `// BUG:` or `// SECURITY:` comment. Fixing the gap makes that test fail, so remove the marker when you fix it.
- Hand-written SQL in a migration must end each statement with `--> statement-breakpoint`, or fresh databases (tests, CI) can't apply it.
- CI (`.github/workflows/ci.yml`) runs on PRs and pushes to `main`. Jobs are named by stage (`check:lint`, `check:migrations`, `check:types`, `build`, `test:unit`, `test:integration`, `test:e2e`, `deploy:migrate`) and run in parallel. Ordering: `test:e2e` needs `build` (reuses the uploaded `.next` output, `E2E_SKIP_BUILD=1`); `deploy:migrate` runs only on pushes to `main`, after every check, in the `Production` GitHub environment (restricted to `main`, secret `DATABASE_URL`), and is never cancelled mid-run. Shared setup lives in `.github/actions/setup`. Vercel's GitHub integration deploys the app itself.

## Architecture

Path alias: `~/*` → `src/*`.

**Routing (App Router):** every route lives in `src/app/<route>/page.tsx`. Pattern used throughout: `page.tsx` is a server component that handles the `auth()` guard (redirect to `/auth/signin`) and static shell, and renders a co-located client component (`*-form.tsx`, `*-list.tsx`, `*-view.tsx`) for interactive parts. Shared page chrome is `src/components/template.tsx`.

**API layer (tRPC 11):** `src/server/api/root.ts` composes `appRouter` from routers in `src/server/api/routers/` — new routers must be registered there manually. `src/server/api/trpc.ts` defines `publicProcedure` and `protectedProcedure` (session-enforcing). **All mutations and sensitive queries must use `protectedProcedure`** (or `adminProcedure` for content management and member data); never select `users.hashedPassword` into a client-facing response (use the `safeUserColumns` pattern in `users.ts`). Zod input schemas live in `src/server/api/schema/schema.ts`. HTTP handler: `src/app/api/trpc/[trpc]/route.ts` (fetch adapter).

**tRPC clients:** client components import `api` (and `RouterOutputs`) from `~/trpc/react` (provider mounted in `src/app/layout.tsx`); server components can use the RSC caller from `~/trpc/server`. The old `~/utils/api` (createTRPCNext) is gone.

**Database (Drizzle + postgres-js):** client in `src/server/index.ts` (`db`). **`src/lib/db/schema/schema.ts` is the single source of truth for all tables** (including NextAuth tables). `drizzle.config.ts` points at `schema.ts`; migrations in `src/lib/db/migrations/`.

**Auth (NextAuth v5 beta / Auth.js):** `src/server/auth.ts` exports `{ handlers, auth, signIn, signOut }` from `NextAuth()` — Google OAuth + credentials (bcryptjs), JWT sessions, Drizzle adapter with explicit table map. Route handler: `src/app/api/auth/[...nextauth]/route.ts`. Use `await auth()` for session access in server components/route handlers. `next-auth` is in `transpilePackages` (next.config.mjs) to work around a beta ESM issue — don't remove it.

**Env vars:** validated in `src/env.mjs` (`@t3-oss/env-nextjs`) — add new vars to both the schema and `runtimeEnv`. Required: `DATABASE_URL`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `NEXT_PUBLIC_GOOGLE_API_KEY`. Optional: `PERKI_BOT_URL` (perki.bot status check, defaults to the Fly.io app; e2e points it at a dead local port), `GOOGLE_DOCS_URL` (where Google Docs are exported from, defaults to docs.google.com; e2e serves fixtures locally), `GOOGLE_SHEETS_URL` (where the Sheets API lives, defaults to sheets.googleapis.com; e2e serves a fixture sheet from the same stand-in) and `DRIVE_FOLDER_URL` (legacy fallback for the Drive folder until it's saved in Settings). Settings staff change without a deploy live in the `settings` table (keys in `src/lib/settings.ts`): the schedule Google Sheet, the takeaway notes and TL;DR documents (Import from Docs), the shared Drive folder (staff open it from the sidebar; writers see a disabled item; hidden when unset), the Discord invite (defaults to the long-standing one) and the WhatsApp group link (only `profiles.whatsappGroup` returns it, and only to members with a complete profile; never in `siteLinks()`). Read the site links with `siteLinks()` from `src/server/settings.ts`. Never hardcode secrets in scripts or source — this repo has had committed secrets before; both were removed and must stay out.

**Styling (Tailwind 4, CSS-first):** all theme tokens live in `src/styles/globals.css` — `@theme` blocks define the brand palette (`cream`, `light-green`, `green`, `dark-green`) and semantic tokens. There is no `tailwind.config.*`. The site ships a single dark-green theme; `.dark` mirrors `:root`. Fonts (`--font-satoshi`, `--font-reimbrandt`) are loaded via `next/font/local` in `src/app/layout.tsx`.

## Design system

General app pages, including the admin login, render inside `src/components/template.tsx`, which owns the page rhythm: one `max-w-2xl` centered column (`width="wide"` widens it to `lg:max-w-3xl` for long reads such as a takeaway), `px-4`, `pt-28 sm:pt-36 pb-24`, centered serif title + muted subtitle, `mt-8 sm:mt-10` gap to content. Pages must not re-introduce their own max-widths, horizontal padding, or top margins. Sign-in and sign-up use a compact card with the same typography and colors. The admin workspace uses its own AdminShell: a stock shadcn sidebar in the sidebar-07 layout (icon-collapsible; keep the primitive's default spacing), with the perki.bot status in its footer, mobile navigation sheet, page heading and action slot. Overview lives at /admin/dashboard; the sidebar nests /admin/groups ("Cooking & cleaning") and /admin/serving ("Serving teams", the serving pool) under a collapsible "Duties" entry (`parent` in `admin-navigation.ts`); the searchable member directory lives at /admin/members and uses one horizontally scrollable data table (member name pinned, on every screen size) and a read-only details sheet opened from the name. Every route has one main landmark linked by the shared skip link.

**Type scale:** `src/styles/globals.css` section 4 defines eleven fluid `type-*` roles (`type-display`, `type-title`, `type-heading`, `type-subheading`, `type-quote`, `type-figure` (sans stat values), `type-lead`, `type-body`, `type-body-sm`, `type-caption`, `type-eyebrow`). Use the role utility for anything a reader reads, never a raw `text-*` size plus breakpoints. Reimbrandt is display-only (never below `type-subheading`); body text is 16px on phones; captions never below 12px. Satoshi ships one weight (500) and synthesis is off, so `font-bold`/`font-light` have no effect on Satoshi text.

**Surfaces:** every surface stays in the green hue family (~169-174), differentiated by *elevation*, never by hue: one OKLCH ramp (hue locked ~183, chroma ~0.03): `background` L.22 → `card` L.27 → `popover` L.30 → `secondary` L.35 → `accent` L.42 (highlight only). **`primary` is the brand cream** so primary actions pop; the whole theme lives in one `:root` block in `globals.css` in canonical shadcn preset format (a ui.shadcn.com theme-editor export can be applied over it with `pnpm dlx shadcn@latest apply <code>`). Content card = `rounded-xl bg-card p-4 sm:p-6` with optional `hover:bg-accent/40`; chips/badges = `rounded-full bg-paper px-2 py-1 text-paper-foreground text-xs`; dialogs = `bg-card` (borderless — no `border` on overlay surfaces or cards); form controls (input, textarea, select, date-picker trigger) are **filled**: `bg-secondary` with a transparent border, never outlined. The owner has asked for this repeatedly, so style the `ui/` primitives, not single forms. Destructive actions use the `destructive` token, never raw red utilities.

**Actions:** always the `Button` component or `buttonVariants()` on a `Link` — never hand-rolled pill divs/links. Hierarchy: `default` = primary action, `secondary` = supporting, `ghost` = quiet (e.g. sign out). Icons inside buttons: `size-4`.

**Color rule:** components use **semantic tokens only** — `bg-background`, `text-foreground`, `bg-accent` (interactive green surfaces), `text-muted-foreground` (secondary/metadata text), `border-accent`, and `bg-paper`/`text-paper-foreground` (the landing page's inverted cream sections and chips). Do not add raw brand-scale values to components; extend the semantic tokens instead. `destructive` is the action fill; `destructive-text` is the lighter, readable validation text color. The landing page (`src/app/page.tsx`, sections in `src/components/home/`) uses `Section` for its vertical sticky titles and alternates `background`/`paper` tones; its hero glow is pure CSS (`.hero-glow` in `globals.css`). New UI must be **mobile-first**: design for ~390px, then enhance with `sm:`/`md:` — most members use the site from their phones.

**UI:** shadcn/ui components in `src/components/ui/` (`components.json`, style "default", RSC). Toasts use **sonner** (`toast.success/error` from `"sonner"`; `<Toaster/>` mounted in the root layout) — the legacy Radix toast was removed. `cn()` helper in `src/lib/utils.ts`. Static content data (events, name lists) lives in `src/lib/data.tsx`.

## Workflow

- Branch from `main` and open a PR into `main`. Merged branches are deleted automatically.
- Work that resolves an issue must put `Closes #<n>` in the **PR description** (one line per issue; `.github/pull_request_template.md` has the slot). GitHub then closes the issue when the PR merges into `main`. A closing keyword in a commit message works too, but the PR description is where it's checked.
- `docs/roadmap.md` is the feature overview; update its row when a PR changes a feature's status.
- The repo is public. Security problems are tracked in private draft security advisories, never in public issues, PRs or commit messages, until they're fixed.

Then `pnpm test:e2e:db`, then write `e2e/screenshots/current.shots.ts` (gitignored, one per change). - **private:** screenshots show e2e seed data only, never the dev or production database. Security problems go to private advisories, never public issues, PRs or commits.

## Admin workspace

- `src/components/admin/` owns navigation, shell, controls, member directory, registration/birthday overview, and dedicated schedule/takeaway/prayer management lists. Public pages contain no admin mutations; on `/prayers`, authors only manage their own requests.
- `/admin/members` URL parameters: `q`, `location` (comma-separated normalised keys), `birthday` (comma-separated months `1`–`12`), `role` (comma-separated roles), `profile` (comma-separated `complete`, `incomplete`, `not-started`), `sort` (`<column>.<asc|desc>`, default `name.asc`), `page`, `pageSize`, `member` (the account id; an older profile id still opens).
- Data tables use `src/components/data-table/` — a tablecn/Dice UI data table ported to TanStack Table v9 and our Radix primitives (the upstream registry ships Base UI only, so don't `shadcn add` it). Column defs set `meta.label`; pinned columns stay opaque. Admin toolbars use `AdminSearch`/`AdminSelect`/`AdminSegmented` from `admin-controls.tsx` (filled `bg-secondary`, no outlines), never native `<select>`. URL state is local (no nuqs): `useSearchParams()` reads it and native `history.pushState`/`replaceState` writes it, which Next.js syncs into the router; filters reset pagination. Details restore focus to the originating button or search on direct entry.
- The directory and dashboard read `profiles.members`: every account, with its `profiles` row or null. Metrics count new accounts by when people joined (`signedUpAt`: the earliest real date of `user.createdAt` and `profiles.createdAt`), with `Europe/Berlin` month boundaries. Instants shared by several rows are the migration `0006` backfill and count as undated, which is disclosed; seed test accounts with distinct dates. The Profiles card counts signed in → started → complete. Date-only birthdays use UTC calendar fields.
- Member details (birthday, phone, where you live, address, studies) live in `profiles`; `profileCompletion()` in `src/lib/profile-completion.ts` decides not started / incomplete / complete for every surface. Name and email come from Google and are read-only (there is no endpoint that changes them; schedule and group links match on the name); members pick an optional `nickname` instead. Members edit their own row on `/account` (`profiles.mine` / `saveMine`, any subset, `""` clears; the user id always comes from the session); `/member/join` redirects there. `/welcome` asks once per account (`user.welcomeSeenAt`, set on save or skip): `WelcomeGate` in `Template` sends anyone due there from app pages (never from `/`, admin or auth pages), and a sign-in with no destination passes through it. Until the profile is complete, `ProfileReminder` shows on app pages (Remind me later snoozes it 7 days per device) and the Account tab carries a dot ("Account, profile incomplete"). e2e accounts are created with `welcomeSeenAt` set; pass `{ welcome: true }` to `createSignedInUser` to test the step. Migrations `0016` (`user.welcomeSeenAt`) and `0017` (`profiles.nickname`) are additive; until `deploy:migrate` applies them, the new release's profile queries fail.
- Prayer migration `0009` adds `visibility`, private by default for existing and new rows. `/admin/prayers` handles review/edit/delete/publication. `/prayers` reads the explicit safe public projection; participant names are never sent by that endpoint. Signed-in acknowledgement uses a locked, idempotent server mutation plus a lookup returning only the current person's acknowledged IDs.
- `deploy:migrate` applies `0009` after merge; until it finishes, the new prayer pages can fail on the missing column (the previous release is unaffected). Development/testing must use the local dev or test database.
- Roles live in the `role` column on `user`: `owner` (exactly one, labelled "Dev" in the UI), `mita`, `writer`, `member` (default). Legacy `admin` is read as `mita`. Admin pages call `requireAdmin()` (`src/server/authz.ts`: sign-in redirect, 404 for members); admin-only tRPC procedures use `adminProcedure`. Takeaway pages use `requireTakeawayAccess()` and takeaway writes use `takeawayProcedure`, which also let writers in. Both read the role from the database on every request, so a JWT never carries stale rights. e2e seeds `ADMIN` (`e2e/fixtures.ts`); `adminLogin()` signs in as it.
- Prayers belong to their author (`prayers.authorId`); only the author or an admin can edit/delete one. Names come from the session, never from input. Requests stay private until an admin publishes them (`setPrayerVisibility`, admin-only); an author's edit sends a published request back to review. Authors see their own requests under "Your requests" on `/prayers`; `acknowledgePrayer` (row-locked, published only) records who prays.
- Takeaways have an author (`takeaways.authorId`, null for older ones). Writers create takeaways and edit/delete only their own; owner and mita manage all. The public takeaway queries never send `authorId`.
- Takeaways move Draft (CaKar) → Submitted → Published (#75; `takeaways.status` `draft` / `in_review` / `published`, migration `0019`; existing rows are published, and the column defaults to `published` so the previous release keeps working). `in_review` means submitted to mita and is labelled "Submitted" everywhere. One shared rule in `src/lib/takeaway-status.ts` decides who may do what; `takeaways.setStatus` enforces it and the admin list and review page show its buttons. The draft is the team's shared working copy: every writer and staff read it on the review page, comment and suggest edits; only the author and staff change its text. The author submits it to mita ("Submit to mita", a dialog) once reviewers' open comments are resolved (`submitBlockers`: unresolved comments from anyone but the writer; the server refuses with a message naming whose), or withdraws it. While submitted the text is locked for everyone (`mayEditTakeaway` is draft-only; deleting stays allowed until published). Only staff (mita and the owner) publish, request changes or unpublish (back to draft, confirmed), so staff are the one gate to the public site. Requesting changes needs a note: it is stored as a staff comment with `takeaway_comments.requestsChanges` (migration `0024`, additive) and shown above the text on the review and edit pages (`ChangesRequested`) until the writer resolves it, which they must before resubmitting. Comments (#57, `src/lib/takeaway-comments.ts`): every writer while it is a draft, its writer also while submitted, staff always. Until `deploy:migrate` applies `0024`, the new release's review threads and status moves fail on the missing column. After publication, edits become a correction (#74, `takeaway_revisions`, migration `0023`): one open revision per takeaway (draft → submitted, labelled "Changes in draft" / "Changes submitted", locked while submitted), the website keeps the published text until staff publish it (which copies it onto `takeaways` and keeps what it replaced as history), and request changes / discard leave the live text alone. The rules are in `src/lib/takeaway-revisions.ts`; comments and suggestions on a takeaway with an open revision apply to the revision (`lockWorkingCopy`), and unpublishing folds an open revision into the draft. Public pages show "Published" and, after a later-day correction, "Updated" (`revisedAt`, published revisions only). Staff act as author for authorless takeaways. Only published takeaways reach `/takeaway`, the public queries and a gathering's `takeawayIds`; publishing records `publishedAt`/`publishedById`.
- Takeaway notes (`takeaways.keypoints`) are Markdown (#35). `src/lib/markdown.ts` holds the shared parse (GFM + `remark-breaks`, so single line breaks stay) and `tidyMarkdown`, which every reader of the text applies first (CRLF, Word's "1.      Title" that would be code, lettered "a." points Tiptap would renumber). `/takeaway/[id]` renders with `TakeawayMarkdown` (react-markdown: raw HTML shown as text, images dropped, external links open in a new tab); previews, reading time and the page description use `markdownToPlainText`. Writers use `MarkdownEditor` (Tiptap v3 + `@tiptap/markdown`, schema in `src/lib/takeaway-editor.ts`). Both are styled by the one `.takeaway-prose` class in `globals.css`, so the editor shows what readers get. `editorRoundTrip`/`rendersTheSame` test that opening and saving a takeaway never changes how it reads; `pnpm takeaways:markdown-check` (read-only) lists stored takeaways that read differently as Markdown or would change in the editor.
- Suggested edits (#58, `takeaway_suggestions`, migration `0022`): on the review page a reviewer selects a passage and chooses Suggest edit (`QuoteablePassage` with `onSuggest`); the rules are in `src/lib/takeaway-suggestions.ts` (writers other than the author and staff while it is a draft; the author and staff decide, also only while it is a draft). Accepting replaces the passage in `keypoints` only when its plain text appears exactly once (`applySuggestion`); otherwise the writer applies it by hand and marks it applied. On the edit page accepting waits for unsaved edits. Suggestions share the review thread's visibility and never reach public queries. Until `deploy:migrate` applies `0022`, the review and edit pages fail on the missing table.
- Review inbox (#59): the Mine view on `/admin/takeaways` shows, above the writer's assignments, Ready to publish (staff: every submitted takeaway), Open feedback (the viewer's unpublished takeaways with unresolved comments from others or open suggestions) and Needs review (others' drafts; for staff only those with open feedback). The rule is `reviewInbox` in `src/lib/review-inbox.ts`; `reviewInbox.mine` only reads. A published takeaway's open correction (#74) counts at the correction's status, with only the comments and suggestions on that correction (`revisionId`); its card shows both badges. Cards open the review page.
- Migration `0010` (roles, `role_changes`, `takeaways.authorId`) has the same deploy window as `0009`: `deploy:migrate` applies it after merge, and until then the new role-aware pages can fail on the missing columns.
- Schedule teams live in `schedule_assignments` (role from `src/lib/serving-roles.ts`, a name, and a `userId` only when exactly one account has that name). The schedule's name columns are still written by the admin forms; add/update re-derive the assignments from them, and `getSchedules` falls back to the columns for schedules without assignments. Cooking/cleaning groups live in `group_terms` → `groups` → `group_members`; a term applies from `startsOn` until the next one starts, and schedules still name their group as text ("Group 3"). Staff manage them on `/admin/groups` (`groups` router, admin procedures; rules in `src/lib/group-terms.ts`): "Start a new term" copies the groups in force before its start date (or six empty "Group 1"…"Group 6") to a date after today, members re-resolved through `resolveAccounts`; staff then add, move (within one term) or remove people. Adding picks a registered member (`MemberPicker` in `src/components/admin/member-picker.tsx`, shared with the serving pool; stored linked to that account) or, through "Not on the site yet", a guest by name. The current and upcoming terms are editable, past ones read-only, an upcoming term can be deleted, and a name appears once per term. `/group` and My duties read the term in force on each day, so they switch on the start date. Migration `0011` copies the existing slots and seeds the April 2026 groups; until `deploy:migrate` applies it, `/group` and `/schedule` on the new release fail. Planning work is tracked in #37.
- People are linked to accounts through `src/server/people.ts`: `resolveAccounts` uses a saved `name_links` spelling (normalised by `nameKey`) first, then an account with exactly that name. Every write of slots or group members goes through it; linking or unlinking on `/admin/names` (staff only, `people` router) relinks every existing slot and group entry with that spelling. Public queries return people as `{ name, image }`: the photo only for signed-in viewers, never the account id. Show people with `PersonAvatar`/`PeopleGrid`/`AvatarStack` (`src/components/person-avatar.tsx`); initials stand in when there is no photo.
- Preachers are guest speakers, never members: the `speakers` table (name with title, photo URL or site path, story, favourite verse, `active`, normalised `aliases`) is managed on `/admin/speakers` (staff only, `speakers` router) and feeds the preacher picker and the landing page's "Our pastors" (`api.speakers.active()`, so `/` renders per request). Preacher slots resolve to `schedule_assignments.speakerId` by name or alias (`src/server/speakers.ts`) and are left out of name links.
